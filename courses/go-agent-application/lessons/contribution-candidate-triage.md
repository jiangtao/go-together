# Day 17：筛选一个值得贡献的问题

返回：[课程目录](../README.md)

## 学习目标

- 把学习中已经观察到的问题收敛成一个可处理候选，先检查是否有人正在解决。
- 候选有实际复现和可解释的边界；发布评论或认领前另行获得授权。
- 最多三个候选的筛选表与一个明确的本地工作范围。

## 先修与边界

先完成 Day 16 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

Issue 标签、assignee 和更新时间只提供线索。评论中的认领、关联 PR、维护者确认与实际复现更能决定是否值得投入。首次任务应有稳定输入、明确 Go 边界和可运行测试，范围比热度重要。

## 动手步骤

1. 从前面实验选择最多三个现象：参数、取消、错误、流式终态或引用不一致。
2. 检查对应 Issue 的评论、关联 PR、分支和认领，不把未分派当作无人处理。
3. 在固定版本复核现象，排除配置问题、已修复版本或只影响个人环境的情况。
4. 为候选记录复现条件、涉及 Go 包、可能验证方法与预期改动规模。
5. 选一个最小候选；若已有修复，则转为验证或补充边界测试，不制造重复 PR。

## 观察与产出

候选有实际复现和可解释的边界；发布评论或认领前另行获得授权。

交付：最多三个候选的筛选表与一个明确的本地工作范围。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。

## 检索问题

- 为什么最新 Issue 活动不能代表维护者已响应？
- 已有 PR 时还有哪些有价值的参与方式？

## 常见误区

先挑标签再找问题，或者只为了提交代码忽略已有实现。
