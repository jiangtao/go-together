# Day 6：问答流与页面状态

返回：[课程目录](../README.md)

## 学习目标

- 流式输出将一个响应拆成多个事件。前端习惯于 append 文本，后端还需要保证状态与终止语义。
- 至少一条链路深入 Go 写流逻辑；不能仅凭最终文本正确判断事件处理正确。
- 事件样本、Go/前端源码位置和三种结束方式的状态表。

## 先修与边界

先完成 Day 5 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

网络读取分块与业务事件边界不同：一次读取可能只有半个事件，也可能包含多个事件。传输断开也不一定是正常完成。必须先识别项目实际使用的协议和终态，再解释页面 loading 状态如何退出。

## 动手步骤

1. 观察一次长回答的响应 Content-Type、原始分块和页面更新方式，确定是 SSE、NDJSON 或其他协议。
2. 从实际请求定位 Go 写流和前端读流代码，分别记录分帧与事件解析规则。
3. 列出开始、文本、工具活动、完成和错误等当前版本实际事件，不补造不存在的事件名。
4. 观察正常结束、服务端报错和客户端断开三种路径。
5. 绘制事件到页面状态的映射，标出谁负责关闭流、发送终态和清理订阅。

## 观察与产出

至少一条链路深入 Go 写流逻辑；不能仅凭最终文本正确判断事件处理正确。

交付：事件样本、Go/前端源码位置和三种结束方式的状态表。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

记录真实浏览器请求与 Go 后端结果；环境、模型或依赖缺失时明确标记尚未完成，不以源码阅读替代本课运行证据。

## 检索问题

- HTTP 200 之后，业务错误还可能出现在哪里？
- 为什么一次 reader.Read 不能当作一条完整事件？

## 常见误区

把 EOF 一律当成功，或假定网络分块总在 JSON 边界结束。
