# Day 1：固定版本与环境基线

返回：[课程目录](../README.md)

## 学习目标

- 先把“我运行的是哪个版本”变成可回答的问题。源码、镜像和文档版本不同，会让页面行为与阅读的 Go 实现不一致。
- 证明入口版本可定位，必要依赖有明确状态。不能因为 Docker 命令存在就认定服务、数据库或模型已可用。
- 一份版本与依赖清单，附实际检查输出及缺失项。

## 先修与边界

具备 Go HTTP、JSON、error、context 与基本测试能力；需要时回到 Go 基础课补齐。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

Git commit 固定源码；镜像 tag 或 digest 固定运行制品；Go 的 go.mod 约束工具链与依赖。这三者不能互相代替。先记录每一层，再判断问题来自产品、配置还是版本混用。

## 动手步骤

1. 从官方仓库固定一个提交，记录 git rev-parse HEAD、go version 和所选启动方式。课程核对过的源码入口见文末；若改用其他版本，更新证据。
2. 读取该提交的 go.mod、README 和启动配置，列出必需服务、模型能力、端口与数据目录；不把可选服务全部打开。
3. 为源码、运行镜像、文档分别记录版本与来源。开发模式直接运行当前源码，镜像模式则核对镜像版本。
4. 执行只读的工具链和容器状态检查，记录缺失依赖；此时不需要调用模型。
5. 写一条最小成功条件：后续应能在一个测试知识库上传并问答。区分环境准备完成与业务闭环完成。

## 观察与产出

证明入口版本可定位，必要依赖有明确状态。不能因为 Docker 命令存在就认定服务、数据库或模型已可用。

交付：一份版本与依赖清单，附实际检查输出及缺失项。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。

## 检索问题

- 为什么固定仓库提交还不足以证明运行镜像一致？
- Go 版本、依赖版本与模型版本各影响哪一层？

## 常见误区

同时升级源码、模型和存储会失去基线；先固定一个可解释的组合。
