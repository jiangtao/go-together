# Day 21：从完整应用抽出 Eino 小服务

返回：[课程目录](../README.md)

## 学习目标

- 能独立追踪 WeKnora 问答后，用更小的服务理解 Agent 框架承担了哪些工作。
- 有边界设计和可验证目标；不能把安装依赖当成跑通 Agent。
- 服务边界图、版本记录和三条行为契约。

## 先修与边界

进入条件是能独立追踪 WeKnora 一次问答请求；沿前课整理已有证据，不以上游贡献是否合并为条件。环境尚未满足时保留缺口，不跳过依赖验证。

gRPC 不是本课前置条件。gRPC 关注服务之间的协议契约、远程调用与状态码；Eino 关注服务内部的模型、工具、上下文与 Agent 执行。本课先使用 HTTP 入口，只有真实跨服务调用需求出现时才补 gRPC。

已有的 context 取消、错误处理与流式测试可以复用。本课新增验证的是这些边界如何穿过 Agent 运行过程，不要求再实现一套相同的基础练习。

基础课的最小 Agent 用来巩固 Go 小接口、脚本测试与资源生命周期。本阶段改用 Eino 承担执行机制，复用已有 Trip 查询、测试场景与业务事件，只补框架适配和运行边界验证；未做基础课 Agent 切片时补最小材料即可，不将整个切片设为硬性前置。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

将 TypeScript 中的异步模型与工具调用映射到 Go 小接口、显式 error 和 context，避免把框架 SDK 类型扩散到业务层。

## 原理与机制

应用负责请求、权限、数据和展示，Agent 运行机制负责模型与工具之间的循环。拆分练习的目的是减少同时变化的因素，不是把 WeKnora 替换掉，也不假定其内部使用 Eino。

## 动手步骤

1. 画出 HTTP → 单 Agent → 一个只读业务工具 → 流式返回，标出 context 和错误边界。
2. 选一个明确的工具，例如从内存测试数据查询 Trip；先不引入完整平台依赖。
3. 按官方 ADK 入门核对 Eino tag、示例 module 和 Go 版本，固定 go.mod/go.sum。
4. 列出应用层数据结构与框架类型的转换点，限制 SDK 类型在适配层内。
5. 定义直接回答、一次工具调用和失败三条验收路径，下一课实现模型替身。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。
