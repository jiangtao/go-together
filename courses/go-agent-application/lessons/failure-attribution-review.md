# Day 16：逐层定位问答失败

返回：[课程目录](../README.md)

## 学习目标

- 用上一课的失败题走完一次归因，而不是从结果直接猜测根因。
- 结论说明已排除哪些解释和仍有哪些不确定性，不能把相关性当成因果证明。
- 逐层证据表、一个单变量验证和可供复现的问题描述。

## 先修与边界

先完成 Day 15 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

故障定位依赖能排除替代解释的证据。解析遗漏、切分丢上下文、检索漏召回、排序压低、上下文裁剪和生成偏离都可能产生相同的错误回答。先找最早出现偏差的边界，再缩小修复范围。

## 动手步骤

1. 挑一题可重复失败的问题，冻结数据和配置。
2. 按原文 → 解析文本 → 片段 → 检索候选 → 排序结果 → 模型上下文 → 回答逐层比较。
3. 标出最早与预期不一致的输出，说明后续错误是否由它传播。
4. 只对该边界改变一个条件，例如注入预期片段；观察最终行为是否随之变化。
5. 整理一次成功对照与一次失败证据，为贡献候选提供最小问题说明。

## 观察与产出

结论说明已排除哪些解释和仍有哪些不确定性，不能把相关性当成因果证明。

交付：逐层证据表、一个单变量验证和可供复现的问题描述。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。

## 检索问题

- 怎样区分根因所在层与最后暴露错误的层？
- 为什么一次变更多个配置会降低定位可信度？

## 常见误区

因为页面显示分数异常就直接修 UI，忽略分数可能在 Go 组装阶段已丢失。
