# Day 9：取消回答的真实语义

返回：[课程目录](../README.md)

## 学习目标

- 从“点击停止”开始调查，确认被停止的是渲染、连接、请求，还是后端工作。
- 能解释每个 context 的所有者和生命周期，区分主动取消与独立后台任务。
- 取消路径图、四类终止情形的语义表和对应 Go 源码位置。

## 先修与边界

先完成 Day 8 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

显式取消是用户意图；网络断开是传输事实；任务终止是服务端行为。这三者需要代码把它们连接起来。后台持久任务可能故意脱离请求生命周期，因此不能一概要求断连后取消所有任务。

## 动手步骤

1. 在固定版本的本地问答中点击停止，观察是否发送取消请求、主动断流或只修改状态。
2. 定位 Go 请求上下文、任务上下文与模型/工具调用的创建位置，标出 context 派生与替换。
3. 寻找取消信号如何按会话或任务身份路由，检查身份是否可能混淆。
4. 分别列出显式停止、刷新页面、网络断开和服务超时的预期语义，依据当前代码与接口约定。
5. 记录实际现象与预期的差异；没有差异也可以完成调查，不预设 bug。

## 观察与产出

能解释每个 context 的所有者和生命周期，区分主动取消与独立后台任务。

交付：取消路径图、四类终止情形的语义表和对应 Go 源码位置。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。

## 检索问题

- 使用 context.Background 创建后台任务会丢失什么？
- 浏览器断流后任务继续，在哪些条件下可能是正确设计？

## 常见误区

仅凭页面停止更新就断言模型调用已退出；或把所有后台任务视为泄漏。
