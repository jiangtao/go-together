# Day 2：启动一个最小知识库

返回：[课程目录](../README.md)

## 学习目标

- 环境的价值是让一次用户操作可复现。首轮只运行一套本地测试环境、一个知识库和一种问答模式。
- 页面、API、文档处理和模型请求分别有证据；启动服务不是本课的全部成功条件。
- 一个知识库的上传和问答记录，以及源码版本、启动方式和脱敏日志。

## 先修与边界

先完成 Day 1 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

进程健康、依赖可达和业务可用是三种状态。HTTP 健康检查成功只说明入口还活着，不能证明解析器、向量索引和模型都能工作。源码调试宜使用官方开发模式，让修改的 Go 代码确实参与请求。

## 动手步骤

1. 按固定版本的开发指南准备本地配置。官方开发入口是 make dev-start、make dev-app、make dev-frontend，分别启动依赖、后端和前端；先核对当前 Makefile。
2. 在独立终端运行后端和前端，记录启动输出与实际地址。端口冲突时使用该版本支持的配置方式更换端口。
3. 在真实 Chrome 中登录本地实例，创建一个测试知识库，配置已有授权的模型与检索所需能力。
4. 上传一份简短的虚构文档，等待处理状态变化，再提出答案明确的问题。
5. 记录浏览器请求、后端日志与处理结果。无法使用模型或依赖时标记具体阻塞，不能把模拟结果写成系统运行通过。

## 观察与产出

页面、API、文档处理和模型请求分别有证据；启动服务不是本课的全部成功条件。

交付：一个知识库的上传和问答记录，以及源码版本、启动方式和脱敏日志。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

记录真实浏览器请求与 Go 后端结果；环境、模型或依赖缺失时明确标记尚未完成，不以源码阅读替代本课运行证据。

## 检索问题

- 健康检查通过但问答失败，应从哪些边界定位？
- 怎样证明请求执行的是本地修改后的 Go 代码？

## 常见误区

开发源码与旧镜像混跑，会让断点永远不命中。
