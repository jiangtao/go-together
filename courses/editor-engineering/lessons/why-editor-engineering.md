# Day 0：为什么值得学习 Web 编辑器工程

English title: **Why Web Editor Engineering Is Worth Learning**

今天不写业务代码。你要先建立一个足以支撑 21 天学习的判断：编辑器不是“在页面上放一个可输入区域”，而是把人的模糊意图稳定地转成结构化数据，并让这些数据可保存、可恢复、可协同、可演进的复杂系统。

## 学习目标

- 解释编辑器对用户、业务、产品平台与工程能力的价值。
- 画出浏览器交互、文档模型、编辑状态、持久化和协同之间的边界。
- 判断为什么本课程选择 ProseMirror，以及哪些需求不该选择它。
- 定义最终编辑器的可见效果、验收标准、非目标和指标体系。
- 写下自己的学习动机、能力缺口和停止条件。

## 背景：编辑器是一种高密度产品基础设施

对用户而言，编辑器是“想法进入产品”的入口。输入是否跟手、粘贴是否保真、撤销是否符合直觉、刷新是否丢失、多人是否互相覆盖，都会直接决定用户是否信任产品。一次光标跳动看似是小缺陷，却会打断思考；一次静默丢稿则可能永久失去用户信任。

对业务而言，文档不是一团 HTML，而是可检索、可授权、可迁移、可分析、可复用的内容资产。结构化标题可以生成目录，链接可以做关系图，任务块可以进入工作流，文档版本可以支持审计。编辑器一旦成为数据入口，就会影响搜索、AI、知识库、审批、协同和开放平台。

对产品平台而言，编辑器往往是多个业务共享的内核。Schema、Command、Plugin 和序列化契约决定了新能力能否以扩展方式进入，而不是每个页面各写一套输入逻辑。一个边界清晰的编辑器平台能复用模型与测试；边界混乱的编辑器会把工具栏、DOM、网络和数据库耦合成无法演进的单体。

对工程师而言，编辑器把前端、领域建模、状态机、数据一致性、分布式系统、性能、安全和可观测性压缩在同一个交互面里。学习它的价值不是多会几个 API，而是训练你在高交互复杂系统中维护不变量的能力。

## 为什么远不只是 contenteditable

contenteditable 解决的是“浏览器允许用户修改一段 DOM”。它复用了排版、输入法、拼写检查、原生选区和辅助功能，这是巨大价值；但它没有替你定义产品的文档结构、命令语义、历史分组、数据版本、持久化确认、协同收敛或权限边界。

同一个用户意图可能经由键盘、工具栏、粘贴、拖放、输入法、浏览器自动更正或远端同步到达。浏览器最终产生的 DOM 还会受浏览器版本、平台、双向文本和 composition 过程影响。如果把 DOM 直接当唯一业务事实源，你很难回答：哪些节点合法、这次变化是不是用户操作、如何撤销、如何映射旧光标、如何在另一台设备重放、如何把并发更新合并。

ProseMirror 没有抛弃 contenteditable。它让浏览器承担擅长的输入与排版，再把文档约束、状态和变换提升为显式模型。你仍然必须理解浏览器，因为引擎与浏览器的边界正是许多疑难问题出现的位置。

## 原理机制：四个相互连接的系统边界

### 1. 结构化文档

文档是一棵受 Schema 约束的树，不是任意 HTML。节点表达段落、标题、列表、引用和代码块；marks 表达强调、链接等行内语义。Schema 是产品契约：它决定什么能存在、如何嵌套、怎样解析、怎样序列化以及未来如何迁移。

### 2. 交互状态

可见文档只是编辑状态的一部分。选区、stored marks、插件状态、composition、历史和 decorations 都会影响下一次操作。用户意图通过 Command 或浏览器事件形成 Transaction；Transaction 由 Steps 描述可映射、可重放的变化。

### 3. 数据持久化

文档 CRUD、自动保存、revision、版本快照、本地持久化和服务端确认属于应用层。编辑器状态更新成功不等于数据已经 durable；显示“已保存”必须有明确确认语义。Schema 版本和迁移属于长期数据责任，不能交给 UI 临时兼容。

### 4. 实时协同

实时协同处理异步网络、重复消息、乱序、离线和并发。内容最终收敛不等于业务语义一定正确：两个人同时改标题可以收敛成一个结果，却仍可能违背产品期望。Presence 和远端光标是短暂状态，不应和持久内容混存。

可以用下面的观察图检查所有权：

    Browser events / DOM Selection
                 ↓
    EditorView ↔ Transaction ↔ EditorState + Schema
                 ↓                    ↕
          Product commands       Yjs binding
                 ↓                    ↕
    Document application       Provider / Awareness
                 ↓                    ↕
    API / durable storage      Update persistence

任何一条箭头都要回答四个问题：谁拥有状态、谁可以修改、失败如何暴露、证据在哪里。

### 核心术语

- structured document：由 Schema 约束的语义树，而不是任意 HTML。
- editing state：文档、选区、历史和插件状态组成的当前编辑快照。
- transaction：把一次编辑意图描述为可检查状态变换的载体。
- durability：数据达到内存、本地磁盘或远端持久层的明确承诺。
- convergence：并发副本在收到相同更新后达到一致结构。
- presence：在线状态、用户标识和远端光标等短暂协同信息。
- source of truth：某类数据唯一可写且能恢复其他投影的权威来源。

## 架构边界与取舍

### 为什么选择 ProseMirror

ProseMirror 的核心优势是结构化、可控与可扩展。官方把它定位为构建富文本编辑器的 toolkit，而非开箱即用组件。它提供明确的文档模型、不可变状态、可映射 Transform/Step、Selection、Plugin 和 View 边界，适合以下场景：

- 产品拥有明确且会演进的结构化文档语义。
- 需要自定义块、marks、命令、粘贴策略和复杂交互。
- 需要可靠历史、位置映射、多人协同或插件生态。
- 团队愿意为控制力承担模型设计、浏览器兼容和测试成本。

本课程选择 ProseMirror，是因为它让编辑器的关键概念保持显式，并与 Yjs 存在成熟绑定。课程不会把 example setup 当生产架构，也不会把第三方包装层当作理解核心机制的替代品。

### 何时不应选择 ProseMirror

以下场景通常先评估更简单方案：

- 只有纯文本或受限 Markdown 输入，textarea 已满足需求。
- 只需少量固定格式，成熟开箱组件的能力与产品高度匹配。
- 团队无法承担 Schema、粘贴、IME、浏览器测试和长期 migration。
- 需求本质是代码编辑器、电子表格、无限画布或像素级分页排版。
- 时间目标只是短期活动页，结构化数据与协同没有长期价值。

“技术更强”不是采用理由。只有控制力带来的产品价值超过复杂度成本时，ProseMirror 才是合理选择。

## 从普通前端到编辑器研发要补齐什么

1. 浏览器编辑语义：Selection、Range、beforeinput、composition、clipboard、focus 与 accessibility。
2. 结构化建模：树、Schema、不变量、版本和 migration，而不是只设计组件 props。
3. 状态与变换：不可变状态、Command、Transaction、Step、mapping 和 history。
4. 分布式判断：revision、幂等、乱序、离线、最终收敛、presence 与冲突语义。
5. 证据工程：property tests、真实浏览器测试、故障注入、profiling、telemetry 与 runbook。
6. 产品取舍：保真与安全、功能与输入延迟、协同可见性与隐私之间的平衡。

## 课程最终目标与可见效果

完成课程后，你应能独立实现并解释一个结构化富文本编辑器：

- 基本 blocks：paragraph、heading、blockquote、ordered/bullet list、list item、code block。
- 基本 marks：strong、emphasis、inline code、link。
- 工具栏、快捷键、选区、粘贴、中文 IME、undo/redo。
- 文档列表以及 create/read/update/delete/restore。
- 自动保存、revision、版本记录、刷新恢复和离线状态提示。
- 多人内容同步、远端光标、断线重连和本地意图撤销。
- 固定夹具下的测试、性能、可靠性、安全、可观测性和部署证据。

## 验收标准

功能“看起来能用”只是一层。最终验收同时要求：

| 维度 | 验收证据 |
|---|---|
| 正确性 | Schema 不变量、Command/Transaction 测试、粘贴与历史序列通过 |
| 性能 | 固定目标环境记录 p50/p95 input-to-paint，无不可解释 Long Task |
| 可靠性 | 刷新、崩溃、断网、重连和重复消息演练不静默丢数据 |
| 协同 | 并发与乱序 updates 最终收敛，远端光标使用相对位置保持语义 |
| 数据安全 | 不信任 HTML 输入；权限在服务端/provider 边界执行；遥测不采集正文 |
| 可运行性 | 错误和同步健康可观察，Schema rollout 可灰度，可回滚 |
| 可维护性 | 模块所有权、ADR、测试矩阵和 runbook 与实现一致 |

## 非目标

- 不从零实现 contenteditable 引擎、OT 或 CRDT。
- 不复刻完整 Notion、Google Docs、Word 或企业知识平台。
- 不实现电子表格计算、分页排版、评论审阅、E2EE 和企业级权限中心。
- 不保证任意 HTML 无损导入。
- 不以代码行数、功能数量或提交次数替代能力证明。

## 指标与获取方法：先学会测，再谈优化

### 质量

记录 Schema 正反 fixtures、关键 Command 分支、历史操作序列、跨来源粘贴 corpus、真实浏览器覆盖和 flaky 次数。覆盖率只能提示未执行代码，不能证明编辑器不变量；关键行为要有可读的场景表。

### 性能

固定设备、浏览器版本、文档夹具和采样方式。至少记录 input-to-paint、transaction apply、React commit、DOM 节点数、序列化、首次协同同步和增量 update 大小。课程暂定大文档夹具为约 5,000 blocks 或 100,000 字符，最终阈值以 Day 17 的基线校准。

### 可靠性

用故障注入而非口头承诺：关闭标签页、刷新、离线、延迟、乱序、重复 update、服务端拒绝、IndexedDB 配额失败、Schema 版本不兼容。记录恢复点目标、恢复时间目标和静默丢写次数。

### 协同收敛

为多个客户端生成并发操作，打乱、重复并分批应用 updates，最终比较结构化文档和 state vector。收敛测试必须可重放失败 seed；“两个窗口肉眼一样”不是充分证据。

### 数据安全

跟踪危险链接/HTML 被拒绝的比例、越权 room 访问测试、敏感遥测扫描、更新持久化完整性和备份恢复演练。文档正文、selection 内容和粘贴原文默认不得进入日志。

## 逐步实验：架构观察

不写实现，只做观察并保存笔记：

1. 打开 ProseMirror 官网示例，输入标题、列表、加粗和链接；观察 DOM 与语义结构是否一一对应。
2. 连续输入后撤销，再执行一次格式命令后撤销；写下你认为的“用户意图分组”。
3. 从网页、纯文本和表格各粘贴一次；记录保留、丢弃和重构了什么。
4. 打开协同示例的两个客户端；人为制造延迟或断连，记录本地响应与最终状态。
5. 阅读指定中文架构文章，只提取“问题、边界、取舍、代价”，不要把案例实现当通用答案。

### 观察点

- 你看到的 DOM 是事实源、投影，还是两者之间的临时同步面？
- 光标属于浏览器、编辑状态还是协同文档？答案是否会因场景改变？
- “保存完成”和“其他客户端已收到”是同一件事吗？
- 一个格式功能需要穿过哪些层？哪一层失败会造成数据损坏？

## 常见失败模式

- 把“做出工具栏”当作会做编辑器，却解释不了文档结构和状态变化。
- 因为 ProseMirror 支持协同，就假设网络、持久化和权限自动解决。
- 看到某篇架构文章的自研方案便照搬，忽略团队、产品和维护成本。
- 用平均延迟掩盖 p95 卡顿，或用单次演示证明可靠性。
- 把 CRDT 收敛等同于用户意图无冲突。

## 判断题

只写“同意/不同意 + 理由 + 边界条件”，本课不提供答案：

1. 只要最终 HTML 正确，编辑过程中的文档模型不重要。
2. CRDT 能保证收敛，因此不再需要版本、备份和冲突产品设计。
3. Presence 反映当前用户状态，所以应和文档内容一起永久保存。
4. ProseMirror 比 textarea 强，因此所有文本输入都应采用 ProseMirror。
5. 性能预算可以直接照搬另一台设备的毫秒数。
