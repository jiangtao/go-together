# Day 20：整理可复查的贡献材料

返回：[课程目录](../README.md)

## 学习目标

- 贡献交付是让维护者可以理解和验证，不以立即合并作为学习完成条件。
- 另一位开发者能按材料复现或验证；无合适新问题时可交付已有修复的验证报告。
- 一份可复查的贡献草稿，含问题、变更、验证与限制。

## 先修与边界

先完成 Day 19 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

问题、触发条件、行为变化、验证和限制形成一条证据链。说明应面向没有参与当前学习过程的人。复现与验证已有 PR 同样有价值，但必须准确区分成果类型。

## 动手步骤

1. 写出一个具体触发场景与修复前后行为，避免仅写“优化体验”。
2. 附固定版本、最小复现和对应 Go 测试，去除令牌、真实文档和本机私有信息。
3. 列出运行过的命令、结果与未运行原因，不能把局部测试说成全平台验收。
4. 核对上游当前贡献说明、目标分支、相关 Issue/PR 与提交要求。
5. 保存本地 Issue/PR 草稿；发送、提交、推送与发布由用户单独决定。

## 观察与产出

另一位开发者能按材料复现或验证；无合适新问题时可交付已有修复的验证报告。

交付：一份可复查的贡献草稿，含问题、变更、验证与限制。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。

## 检索问题

- 维护者需要哪些信息才能区别环境问题与产品缺陷？
- 为什么已合并不等于测试充分，未合并也不等于学习失败？

## 常见误区

只贴通过截图、没有输入与版本；或者把别人的修复描述为自己的新贡献。
