# Day 26：比较平台与框架的职责

返回：[课程目录](../README.md)

## 学习目标

- 把 Eino 小服务与 WeKnora 放在同一个问题下比较，形成自己的工程判断。
- 比较基于同一目标，明确证据和限制；不猜测 WeKnora 的内部依赖关系。
- 两条路径、职责对照表与一项需求变更分析。

## 先修与边界

先完成 Day 25 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

将 TypeScript 中的异步模型与工具调用映射到 Go 小接口、显式 error 和 context，避免把框架 SDK 类型扩散到业务层。

## 原理与机制

框架封装执行机制，平台还拥有知识、权限、任务、存储和用户体验。比较时需要固定业务目标，分别列出复用能力、自己承担的责任和故障边界，不能用代码行数简单判断优劣。

## 动手步骤

1. 选择同一个只读问答任务，分别画出 WeKnora 和 Eino 小服务的路径。
2. 比较模型上下文、工具调用、状态保存、流式返回和取消的责任方。
3. 为每个结论附真实源码或测试，缺失能力标为未实现而不是默认框架提供。
4. 讨论一项扩展需求，例如多轮会话，说明两种方案分别需要改哪些边界。
5. 写出继续在 WeKnora 贡献和使用 Eino 新建小服务的适用条件。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。

## 检索问题

- 哪些平台功能不应被误认为 Agent 框架自动提供？
- 复用一个框架会转移哪些责任，又保留哪些责任？

## 常见误区

因为小服务更短就认为平台设计多余，忽略被省略的业务约束。
