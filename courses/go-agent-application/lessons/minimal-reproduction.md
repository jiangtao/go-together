# Day 18：构造最小复现与失败测试

返回：[课程目录](../README.md)

## 学习目标

- 一份好的复现能让不了解对话背景的人看到同一个错误。
- 失败断言直接对应问题；随机性、网络和环境缺失要被控制或明确标注。
- 最小输入、稳定失败测试、实际输出及正常对照。

## 先修与边界

先完成 Day 17 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

最小复现逐步去掉无关输入与依赖，同时保持失败。回归测试应在修复前稳定失败、修复后通过，并断言用户可观察的行为。仅断言某个函数被调用容易锁死实现细节。

## 动手步骤

1. 记录固定 SHA、平台、配置范围、输入与预期/实际结果。
2. 从现有请求或测试减少字段、文档规模和依赖，直到再删就不触发问题。
3. 定位最小 Go 测试边界，使用项目现有 fixture 或替身。
4. 重复运行失败用例，确认失败原因与目标问题一致，而不是网络或环境错误。
5. 加入一个合法输入对照，说明修复不能破坏的邻近行为。

## 观察与产出

失败断言直接对应问题；随机性、网络和环境缺失要被控制或明确标注。

交付：最小输入、稳定失败测试、实际输出及正常对照。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证命令

在当前练习的 Go 模块根目录运行下面的命令。对上游源码应先选实际目标包；不把其他模块的通过当作本课证据。需要网络、真实模型或数据库时，另记录环境与系统验证结果。


## 检索问题

- 最小复现和全链路复现各提供什么证据？
- 测试失败于依赖初始化时能否证明目标 bug 存在？

## 常见误区

把整个数据库或私人日志交给维护者，既难重现也扩大信息暴露。
