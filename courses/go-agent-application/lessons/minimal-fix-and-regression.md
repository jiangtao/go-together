# Day 19：最小修复与回归范围

返回：[课程目录](../README.md)

## 学习目标

- 修复只改变已经证明错误的行为，并用证据解释为什么不会破坏邻近路径。
- 前后测试使用相同条件；若验证已有 PR，明确测试的 PR/SHA，不声称自己实现了修复。
- 最小 diff、修复前后结果、邻近行为检查与剩余限制。

## 先修与边界

先完成 Day 18 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

修改越跨层，可能回归的行为越多。先在拥有该业务约定的边界修复，沿用现有错误、接口和测试风格。不要为局部 bug 同时重写路由、存储和前端状态管理。

## 动手步骤

1. 阅读目标包一至三个邻近实现与测试，确认数据和生命周期的所有者。
2. 保留失败测试，修改造成偏差的最小代码路径。
3. 运行同一用例确认从失败变通过，再运行目标包的邻近测试。
4. 涉及共享状态或取消时加 race 检查；涉及前端显示时再走真实 Chrome 的对应操作。
5. 检查 diff，删去与问题无关的格式、依赖和重构变化。

## 观察与产出

前后测试使用相同条件；若验证已有 PR，明确测试的 PR/SHA，不声称自己实现了修复。

交付：最小 diff、修复前后结果、邻近行为检查与剩余限制。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证命令

在当前练习的 Go 模块根目录运行下面的命令。对上游源码应先选实际目标包；不把其他模块的通过当作本课证据。需要网络、真实模型或数据库时，另记录环境与系统验证结果。

```bash
go test ./...
go test -race ./...
```

## 检索问题

- 为什么修复应落在拥有契约的层，而不是最容易改的层？
- 什么变化会要求扩大回归范围？

## 常见误区

删除失败断言让测试变绿，或者用吞掉所有错误的方式掩盖问题。
