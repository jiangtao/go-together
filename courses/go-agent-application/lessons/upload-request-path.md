# Day 3：从上传操作追到 Go 业务逻辑

返回：[课程目录](../README.md)

## 学习目标

- 利用熟悉的浏览器 Network 面板，把上传操作映射到服务端真实函数。目标是追踪数据，不是浏览所有目录。
- 请求中的一个具体字段能够追到 Go 业务使用处；能区分请求失败与异步处理失败。
- 一次上传的脱敏请求摘要、5-8 个节点的调用图和字段映射表。

## 先修与边界

先完成 Day 2 的关键产物；环境尚未满足时保留缺口，不跳过依赖验证。

本课围绕一个明确问题推进。项目版本与真实行为以固定源码、配置和运行结果为准；本教程的课文完整不代表学习者已经完成实验。

## Node.js 对照

从熟悉的页面请求、异步状态和错误处理出发；在 Go 中额外追踪显式 error、context 传播、接口边界与数据所有者。

## 原理与机制

页面表单、HTTP 请求、Go DTO 和业务对象分别属于不同边界。文件上传被接收与内容成功入库通常是两件事；请求 ID、文档 ID 和任务 ID 也可能是不同身份。

## 动手步骤

1. 上传一份只有两段文本的测试文件，记录请求方法、路径、字段名称和响应状态，去除认证信息。
2. 以实际路径中的稳定片段搜索后端路由注册，再定位 handler 和请求结构。
3. 追到第一次业务 service 调用，记录它接收哪些字段、生成哪个身份、返回什么。
4. 找到成功响应之前最后一个持久化或任务提交点，解释响应承诺的是“接收”还是“处理完成”。
5. 画出页面 → 请求 → 路由 → handler → service → 返回的调用图，每个节点附固定版本源码位置。

## 观察与产出

请求中的一个具体字段能够追到 Go 业务使用处；能区分请求失败与异步处理失败。

交付：一次上传的脱敏请求摘要、5-8 个节点的调用图和字段映射表。

证据需能定位到当前版本与具体行为；观察事实和个人推断分别写清。

## 验证方式

检查每项产物的版本、源码位置与判断依据。本课不要求为了形式运行不相关的测试；引用前课验证时必须指明具体行为和结果。

## 检索问题

- 响应成功是否意味着文档已经可以检索？
- 为什么不能拿前端临时 ID 代替后端任务 ID？

## 常见误区

只找到路由就停止，会漏掉参数默认值和真正业务判断。
